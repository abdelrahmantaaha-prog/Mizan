Chapter 1

What this thing actually is

A net-worth tracker built for holdings that are not all in one currency, and not all in currency at all.

Most money apps assume one currency and a bank that tells you the balance. Mizan assumes neither. An Egyptian portfolio is EGP in one account, dollars in another, and gold by the gram at 21 or 24 karat — three units that only become one number when you multiply by today's prices.

part 1

A Vite React app

A single-page app, deliberately not Next.js. It builds to static files and runs entirely in the browser — which is what makes “works with no backend” a true statement rather than a marketing one.

the source of truth

One document in localStorage

Accounts, transactions, debts, recurring rules, daily history, price history, plus three scalar maps. Everything else in the app is derived from it.

part 3

The price feed

Gold and USD/EGP, from three routes in order of cost: a serverless proxy, the public APIs direct, and — last resort — an AI with search grounding that can read the Egyptian صاغة market.

part 4, optional

Express + Auth.js + Neon

The sync backend, running as one Vercel function. Without the environment variables the app runs local-only and says so in Settings rather than showing a broken sign-in button.

The sentence that explains the whole design

Mizan is local-first with a live price layer. Two consequences follow, and they pull in opposite directions. Because it is local-first, two devices can edit offline and the merge must resolve without a referee. Because prices are live, the same holding is worth a different number every day — and that is desirable for balances and catastrophic for history.

Chapter 3 is how those two facts are reconciled, and it is the most important idea in the codebase.

Check yourself: which number on the Overview screen exists nowhere in storage?

Read the top of shared/model.js

It opens with a constraint rather than a description: “Keep this file free of DOM, React, Node and network APIs.” That is not style advice. api/ imports it inside a Vercel function and src/ imports it into the browser bundle, so a single window. or require() in that file breaks one side or the other — and it will break the side you are not currently testing.

Look at what has tests and what does not. Activity.jsx is 783 lines and has none; valuation.js is 101 lines and has ten. That is not neglect — it is the same discipline as Rhythm's. Every rule that would be expensive to get wrong has been pulled out of the UI into a file that takes values in and returns values out, and those files are where every test lives.

Chapter 3

The rule that stops history rewriting itself

A balance is worth today's price. A transaction is worth what it was worth when it happened. Confusing the two is the bug this file was written to kill.

Here is the failure in plain terms. You logged a $100 dinner last year. If the app values that transaction at today's rate, then every time the pound weakens, last year's dinner gets more expensive — and your “spent in March” total moves on its own, months after March ended.

The fix is a single discipline: capture the rate at the moment of logging, and read the snapshot forever after.

The capture happens once, when a transaction is written.

And the read has a fallback chain, because data outlives the accounts that made it.

The general lesson

This distinction has a name in accounting — historical cost versus fair value — and it appears in far more systems than money apps. Anything you record has two possible valuations: what it is worth now, and what it was worth then. Ask which one each screen needs, and store the second one at write time, because it can never be reconstructed later.

Check yourself: you delete the account a two-year-old expense was paid from. What happens to that expense in the Spending tab?
Chapter 4

One document, six collections, three scalars

The shape of the data is chosen so that merging two copies is possible at all. Everything about it is a sync decision in disguise.

Why soft deletes

A hard delete is invisible. Device A removes a row and pushes; device B never knew about the removal, still has the row, and pushes it back. The row returns from the dead and the user cannot understand why. A tombstone makes the deletion a fact that can travel — and because it carries a timestamp, it competes fairly against a later genuine re-creation.

Tombstones are not kept forever: TOMBSTONE_TTL_DAYS = 120 is a bet that no device stays offline for four months. That is the right shape of trade-off to notice — a correctness guarantee traded for bounded storage, with the assumption written down.

Migration: accepting whatever arrives

migrate() runs on every document that enters the app, from any source — old localStorage, an imported backup file, a push from the server. There is no path into the app that skips it, and that single fact is why the rest of the code can assume a well-formed shape.

Chapter 5

The merge, record by record

Both devices push their whole document. The server merges blindly. No change log, no vector clocks, no reconciliation code on the client.

That is only possible because the merge has two mathematical properties. It is symmetric — merge(a,b) and merge(b,a) hold the same content — and idempotent — merging twice changes nothing. Together they mean the server does not need to know who edited what, in which order, or whether it has seen this request before.

And the whole-document merge that drives it, which also does two things that are easy to miss.

What this costs you

Last-write-wins per record means exactly what it says: if you genuinely edit the same account on two devices while both are offline, one of those edits is discarded and nothing tells you. That is a real cost, accepted deliberately in exchange for a merge that needs no user interface, no conflict dialog and no server state. Logging an expense on your phone while editing an account on your laptop keeps both, because those are different records — which is the case that actually happens.

The same fingerprint story

Mizan carries the same fingerprint() / stable() pair as Rhythm, for the same reason: deciding “has this changed?” with JSON.stringify compares key order, and the server builds the merged document in a different order than migrate() does on the way back in. Unchanged documents then compare unequal on every round trip, and the client pushes, adopts, sees a difference, and pushes again — forever, while the user is trying to type.

Both projects fixed it the same way, and the fix is nine lines: sort the keys, drop undefined, recurse.

Check yourself: two devices touch the same account in the same millisecond — one edits it, one deletes it. Which wins?
Chapter 6

Prices: three routes and a plausibility gate

Every number in the app is multiplied by these two figures. Getting a wrong one is worse than getting none.

The pattern worth stealing

inGoldRange and inFxRange are two lines that prevent a whole class of disaster. A parser that grabs the wrong number from a page — a page count, a percentage, a timestamp — will hand you something numerically valid and financially absurd. Bounding the answer to what is plausible turns a silent repricing of the entire portfolio into a clean failure that falls through to the next route.

Whenever you ingest a number from a source you do not control, ask what range it could sanely be in, and reject outside it. It costs two lines and it is the difference between an app that is wrong and an app that says it does not know.

The route order is the interesting part, and it is ordered by cost to the user, not by convenience. The proxy first, because it fetches server-side — so the browser's CORS rules and the sandboxes that used to leave the app stuck on “blocked” never come into it, and the response is cached for everyone. Then the public APIs direct, which works on the open web and keeps the app functional for anyone running it without the backend. Only last, the AI with search grounding: it costs tokens, and it is the only route that can read the Egyptian صاغة market rather than derive a local price from the global spot.

Note that the last route is also the most accurate one for this specific market, and it is still last. Accuracy is not the only axis.

Check yourself: all three routes fail. What does the app show, and how does the user know?
Chapter 7

Zakat: a threshold, a clock, and an admission

Eighty-two lines that encode a religious obligation — and, more importantly, know where their own authority ends.

Two things the earlier version of this card got wrong, and the file names both at the top rather than hiding them.

The honesty that matters most

“This is still an estimate, not a ruling.” Intent, business inventory, debt treatment and the choice of standard are all matters for someone qualified — and the card says so on screen, not just in a comment. When your software touches a domain with real authorities in it — medicine, law, religion, tax — the most professional thing it can do is be precise about the boundary of what it is claiming.

The hawl clock, and the function that returns undefined

Zakat is owed on wealth that stayed above the threshold for a full lunar year. So the card needs a clock: a start date, stored, that resets if you fall below. Which creates a classic React trap — a component that computes a new value on every render and writes it back will re-render forever.

Check yourself: nextHawlStart can return a date, null, or undefined. Why does it need all three?
Chapter 8

Two features defined by what they refuse to do

Recurring transactions do not post themselves. The AI never sees your data unless you ask it to.

The reasoning

Automatic posting is the obvious feature and it is the wrong one here. Silently writing money movements you never saw makes every balance in the app slightly suspect — and a net-worth tracker you do not fully trust is worse than no tracker, because you will act on it anyway. Proposing and confirming costs one tap and buys total confidence in the numbers.

The MAX_CATCH_UP cap is the same instinct applied to the failure case: a rule ignored for two years should not dump a hundred back-dated rows into your history the moment you open the app.

The AI layer, and Google's moving target

Rule

Never pin a dated model id. gemini-2.5-flash looks stable and is a time bomb — providers retire dated ids on their own schedule and your app dies on a day you were not deploying. The -latest aliases are maintained by Google to point at the current model; use those, and keep a fallback chain behind them for the day even an alias moves.

Check yourself: a user never enters a Gemini key. What stops working?
Chapter 9

Change it yourself

Four exercises, in order of difficulty. Each one uses a different layer of what you have just read.

  1. Add a spending subcategory. TAXONOMY in shared/model.js. One line, and it appears everywhere — which is the payoff of a single source of truth.
  2. Add a karat. 18-karat gold is common in Egypt. karatPrice already handles any karat arithmetically; find where the pickers offer the fixed list and extend it. Then check the Prices screen still reads sensibly.
  3. Add a currency. Euros, say. unitRate, the price fetch, the plausibility gate, the unit label, and the pickers. Notice how much of the app you do not have to touch — that is what the valuation layer bought you.
  4. Add a collection. Track subscriptions as first-class records. Add to COLLECTIONS, then migrate, then a merge test proving two devices editing different subscriptions both keep their work. Every skill in this tour, in one feature.

Running it

npm run dev

That serves the frontend only, and sync correctly reports itself unavailable — a supported way to work on the UI. For the API you need vercel dev.

npm test

Forty-six tests over five files: merge, migration, the sync push path, valuation, and zakat. Run them before every change to any of those five.

Habits that separate professionals from hobbyists

  • Ask “now or then?” about every stored number. Chapter 3 is one instance of a question worth asking in every system you build.
  • Bound every number you did not compute yourself. Two lines of plausibility check beat a week of wondering why the portfolio jumped.
  • Soft-delete anything that syncs. A hard delete cannot travel, and undeletion is the most confusing bug a user can experience.
  • Say what you do not know. “fallback baseline”, “estimate, not a ruling”, “sync unavailable” — three places where this app declines to bluff, and each one buys trust in everything else it says.
  • When you cannot explain it, you do not understand it yet. Try explaining why mergeState is symmetric out loud. The gaps announce themselves.
